NORTHSTAR EDGE GATEWAY Technical Operations and System Specification
Document ID: NS-EG-204 Version: 1.4 Publication date: 2026-10-18
Classification: Internal engineering test documentation

====================================================================== 1.
PURPOSE AND SCOPE
======================================================================

This document describes the fictional Northstar Edge Gateway (NEG), a
service that receives telemetry from industrial sensors, validates it,
stores accepted events, and exposes query and administration APIs.

The document is intentionally self-contained. It is suitable for testing
document ingestion, chunking, semantic retrieval, metadata filtering,
multi-hop question answering, and grounded response generation in a
retrieval-augmented generation (RAG) system.

Northstar Edge Gateway is a fictional system. All hostnames,
identifiers, people, limits, and operational procedures in this document
are invented for testing.

The system has four primary components:

1.  Ingest API: accepts sensor events over HTTPS.
2.  Validation worker: checks schema, device registration, and event
    time.
3.  Event store: persists validated events in PostgreSQL.
4.  Query API: allows authorized clients to retrieve event history and
    service health information.

The gateway does not directly control industrial machinery. It receives
measurements and reports status; it must not be used as a safety
controller.

======================================================================
2. SYSTEM OVERVIEW
======================================================================

2.1 Deployment topology

A standard deployment contains the following services:

-   edge-api: HTTP API service, default internal port 8080.
-   validation-worker: asynchronous event validation process.
-   postgres-primary: PostgreSQL 16 database.
-   redis-cache: Redis 7 cache and short-lived coordination store.
-   object-archive: S3-compatible object storage for daily exports.
-   metrics-agent: Prometheus-compatible metrics exporter.

The public API is exposed through a reverse proxy. The reverse proxy
terminates TLS and forwards requests to edge-api over the private
service network.

Production service DNS names:

-   api.northstar.example: public API hostname.
-   edge-api.service.local: internal API service.
-   postgres-primary.service.local: primary database.
-   redis-cache.service.local: cache service.
-   object-archive.service.local: archive endpoint.

The hostname api.northstar.example is a documentation placeholder and
does not resolve to a real production system.

2.2 Request lifecycle

A normal telemetry request follows this sequence:

1.  A device sends an HTTPS POST request to /v1/events.
2.  The reverse proxy validates the TLS connection and forwards the
    request.
3.  edge-api checks the API token and basic request size.
4.  edge-api writes the event to the ingestion queue.
5.  validation-worker checks the event schema and device registration.
6.  Accepted events are inserted into PostgreSQL.
7.  The worker updates the device’s last-seen timestamp.
8.  The API returns an ingestion receipt to the original client.

The API acknowledges queue acceptance, not necessarily database
persistence. A client that needs confirmation of persistence must query
the event by its event_id or inspect the event processing status
endpoint.

2.3 Availability targets

The monthly availability objective for the public API is 99.9 percent.
The ingestion service target is 2,000 events per second per regional
deployment under the reference workload.

The normal API response-time objective is: - p50: below 80
milliseconds. - p95: below 250 milliseconds. - p99: below 700
milliseconds.

These are service objectives, not guarantees. They apply to requests
measured at the reverse proxy and exclude client-side network delay.

======================================================================
3. EVENT DATA MODEL
======================================================================

3.1 Event structure

Every event contains the following required fields:

-   event_id: globally unique UUID generated by the device.
-   device_id: registered device identifier.
-   tenant_id: organization identifier.
-   event_type: measurement category.
-   observed_at: UTC timestamp when the device measured the value.
-   received_at: UTC timestamp assigned by edge-api.
-   sequence_number: monotonically increasing number per device.
-   payload: JSON object containing measurement values.

Example event:

{ “event_id”: “8c8a8e6d-0a70-4d8f-a2f7-9a4e2a113001”, “device_id”:
“pump-17”, “tenant_id”: “tenant-aurora”, “event_type”: “temperature”,
“observed_at”: “2026-10-18T08:15:30Z”, “received_at”:
“2026-10-18T08:15:31Z”, “sequence_number”: 1842, “payload”: { “value”:
72.4, “unit”: “celsius”, “sensor_channel”: “outlet” } }

3.2 Event types

Supported event types in version 1.4 are:

-   temperature: numeric temperature reading.
-   vibration: vibration velocity in millimeters per second.
-   pressure: pressure reading in kilopascals.
-   status: device status message.
-   power: electrical power reading in watts.

An event with an unrecognized event_type is rejected with error EVT-004.
A recognized event_type with a missing or invalid payload is rejected
with error EVT-005.

3.3 Timestamp rules

All timestamps must use ISO 8601 format with an explicit timezone. The
service stores timestamps in UTC.

The maximum accepted clock skew is 300 seconds into the future relative
to the validation worker’s synchronized clock. Events more than 300
seconds in the future are rejected with EVT-009.

Events older than 30 days are accepted only through the administrative
backfill endpoint. The normal ingest endpoint rejects them with EVT-010.

The service does not rewrite observed_at to received_at. These fields
represent different moments and must remain distinct.

3.4 Sequence numbers

A device should increase sequence_number by one for each event. A gap is
recorded as a warning but does not automatically reject the event. A
duplicate sequence number is rejected with EVT-012 unless the request is
an exact retry with the same event_id and identical content.

======================================================================
4. TENANCY AND AUTHORIZATION
======================================================================

4.1 Tenant isolation

Northstar uses a shared PostgreSQL database and shared application
schema. Tenant-owned rows contain a tenant_id column.

The application derives tenant_id from the validated API token. It must
not trust a tenant_id supplied only in the request body or query string.

Every tenant-scoped database query must include a tenant restriction.
For example:

SELECT event_id, device_id, observed_at, payload FROM telemetry_events
WHERE tenant_id = $1 AND device_id = $2 ORDER BY observed_at DESC LIMIT
100;

The first parameter is the tenant identifier obtained from the
authenticated request context. The second parameter is the requested
device identifier.

PostgreSQL row-level security (RLS) is enabled for telemetry_events in
production. The application sets the transaction-local value
app.current_tenant before executing tenant-scoped queries.

4.2 Authorization roles

The system defines four roles:

-   tenant_viewer: can read events and device status within one tenant.
-   tenant_operator: can read events and update device metadata.
-   tenant_admin: can manage users, API tokens, and tenant settings.
-   platform_operator: can inspect cross-tenant service health but
    cannot read tenant payloads through the ordinary administration
    interface.

A tenant_operator cannot create another tenant_admin. Only an existing
tenant_admin or an authorized platform provisioning workflow can grant
that role.

4.3 API token handling

API tokens are shown only once at creation time. The database stores a
cryptographic hash of each token, not the original token.

Tokens can be revoked immediately. Revocation is checked against the
token cache, which has a maximum time-to-live of 60 seconds. Emergency
revocation also publishes an invalidation message to Redis.

======================================================================
5. HTTP API REFERENCE
======================================================================

5.1 Submit an event

Method: POST Path: /v1/events Authentication: Bearer API token
Content-Type: application/json

Success response: HTTP 202 Accepted

Example response:

{ “event_id”: “8c8a8e6d-0a70-4d8f-a2f7-9a4e2a113001”, “status”:
“queued”, “accepted_at”: “2026-10-18T08:15:31Z” }

HTTP 202 means the event has entered the processing queue. It does not
mean the event has already been committed to PostgreSQL.

5.2 Retrieve an event

Method: GET Path: /v1/events/{event_id} Authentication: Bearer API token

Possible responses: - 200: event found and visible to the authenticated
tenant. - 404: event does not exist or is not visible to the tenant. -
401: token missing, invalid, or revoked. - 429: request rate limit
exceeded.

The API intentionally returns 404 for an event belonging to another
tenant. It does not disclose that another tenant owns the event.

5.3 List device events

Method: GET Path: /v1/devices/{device_id}/events Authentication: Bearer
API token

Supported query parameters: - from: inclusive UTC timestamp. - to:
exclusive UTC timestamp. - limit: integer from 1 through 500; default
100. - cursor: opaque pagination token.

If limit is greater than 500, the API returns HTTP 400 with error
API-021. If from is later than or equal to to, the API returns HTTP 400
with error API-022.

5.4 Device status

Method: GET Path: /v1/devices/{device_id}/status

The response includes: - device_id - connection_state - last_seen_at -
last_event_type - last_sequence_number

A device is considered stale when no event has been received for more
than 15 minutes. A stale device is not automatically considered offline;
the status is reported as stale until the device-specific offline
threshold is reached.

5.5 Health endpoint

Method: GET Path: /health Authentication: none on the private network;
restricted on public ingress.

The health endpoint reports whether the API process can serve requests.
It does not prove that every downstream dependency is healthy.

The detailed readiness endpoint is /ready. It checks PostgreSQL, Redis,
and the ingestion queue. A failed dependency causes HTTP 503.

======================================================================
6. DATABASE DESIGN
======================================================================

6.1 Main tables

tenants - tenant_id UUID PRIMARY KEY - name VARCHAR(120) NOT NULL -
created_at TIMESTAMPTZ NOT NULL

devices - device_id VARCHAR(80) NOT NULL - tenant_id UUID NOT NULL
REFERENCES tenants - display_name VARCHAR(120) - registered_at
TIMESTAMPTZ NOT NULL - last_seen_at TIMESTAMPTZ - PRIMARY KEY
(tenant_id, device_id)

telemetry_events - event_id UUID PRIMARY KEY - tenant_id UUID NOT NULL -
device_id VARCHAR(80) NOT NULL - event_type VARCHAR(32) NOT NULL -
observed_at TIMESTAMPTZ NOT NULL - received_at TIMESTAMPTZ NOT NULL -
sequence_number BIGINT NOT NULL - payload JSONB NOT NULL

api_tokens - token_id UUID PRIMARY KEY - tenant_id UUID NOT NULL -
token_hash BYTEA NOT NULL - role VARCHAR(32) NOT NULL - revoked_at
TIMESTAMPTZ - created_at TIMESTAMPTZ NOT NULL

6.2 Indexes

The following indexes are required:

-   telemetry_events(tenant_id, device_id, observed_at DESC)
-   telemetry_events(tenant_id, event_type, observed_at DESC)
-   devices(tenant_id, last_seen_at DESC)
-   api_tokens(token_id)

The primary key on event_id supports direct event lookup. The composite
tenant/device/time index supports the most common device history query.

6.3 Partitioning

telemetry_events is partitioned by RANGE on observed_at, using monthly
partitions.

The partition named telemetry_events_2026_10 contains events whose
observed_at timestamp is greater than or equal to 2026-10-01 00:00:00
UTC and less than 2026-11-01 00:00:00 UTC.

A partition for the next month must be created at least seven days
before the month begins. The partition maintenance job runs daily at
02:20 UTC.

If a required partition is missing, inserts can fail even when the
database itself is healthy. The alert code for this condition is DB-031.

6.4 Retention and archival

Hot telemetry remains in PostgreSQL for 90 days. At the end of the
retention period, eligible monthly partitions are exported to object
storage in compressed Parquet format and then detached and dropped after
verification.

Archived data is retained for 24 months. The archive verification job
checks the object count, manifest checksum, and total row count.

The system must not drop a database partition if archive verification
has not completed successfully.

======================================================================
7. VALIDATION AND ERROR CODES
======================================================================

The validation worker performs checks in this order:

1.  Parse JSON and validate required fields.
2.  Confirm that the device is registered to the authenticated tenant.
3.  Validate event_type and payload structure.
4.  Validate timestamp format and clock skew.
5.  Check event_id idempotency.
6.  Check sequence number consistency.
7.  Persist the accepted event.

Error catalogue:

EVT-001: malformed JSON. EVT-002: required field missing. EVT-003:
invalid field type. EVT-004: unsupported event_type. EVT-005: invalid
event payload. EVT-006: device not registered to tenant. EVT-009:
observed_at exceeds future clock-skew allowance. EVT-010: event is too
old for normal ingestion. EVT-012: duplicate sequence number with
conflicting event content. EVT-013: event_id reused with different
content.

API-021: limit exceeds maximum allowed value. API-022: invalid time
range. API-030: cursor is malformed or expired.

DB-031: expected time partition is missing. DB-032: database connection
pool exhausted. DB-033: transaction serialization retry limit exceeded.

SEC-001: API token invalid. SEC-002: API token revoked. SEC-003: tenant
context missing from database transaction. SEC-004: authorization role
insufficient.

======================================================================
8. PERFORMANCE AND CAPACITY
======================================================================

8.1 Reference environment

The reference performance environment uses:

-   8 vCPU for edge-api.
-   8 vCPU for validation-worker.
-   32 GB RAM for PostgreSQL.
-   NVMe-backed database storage.
-   1 Gbps private network.
-   PostgreSQL connection pool maximum of 40 connections per API
    instance.

The reference environment is a benchmark configuration, not a minimum
hardware requirement.

8.2 Backpressure

The ingestion queue has a soft capacity threshold of 70 percent and a
hard capacity threshold of 90 percent.

At 70 percent, the service emits a warning and increases queue-depth
metrics sampling. At 90 percent, edge-api returns HTTP 429 for new
ingestion requests unless the caller has an approved priority token.

The service must not silently discard events to reduce queue depth.

8.3 Retry policy

Clients may retry transient failures using exponential backoff with
jitter. The recommended schedule is 1 second, 2 seconds, 4 seconds, 8
seconds, and 16 seconds, with a random jitter of up to 500 milliseconds.

Clients must reuse the same event_id and identical event content when
retrying an event. Creating a new event_id for an unchanged retry can
produce duplicate logical measurements.

The client should stop automatic retries after five attempts and report
the failure to its operator.

======================================================================
9. SECURITY REQUIREMENTS
======================================================================

-   TLS 1.2 or newer is required for external connections.
-   API tokens must never be written to application logs.
-   Database credentials must be loaded from the deployment secret
    store.
-   Tenant identity must come from authenticated server-side context.
-   SQL statements must use parameterized queries.
-   Administrative actions must be recorded in the audit log.
-   Archive objects must use server-side encryption.
-   Production database access is restricted to approved service
    identities and on-call personnel.
-   Debug endpoints must not be exposed through public ingress.

Audit records include actor_id, tenant_id when applicable, action,
resource_id, request_id, timestamp, and outcome. Audit records are
append-only for application users.

10. MONITORING AND ALERTING
======================================================================

Important metrics:

-   northstar_ingest_requests_total
-   northstar_ingest_rejected_total
-   northstar_queue_depth
-   northstar_validation_duration_seconds
-   northstar_database_query_duration_seconds
-   northstar_api_request_duration_seconds
-   northstar_device_last_seen_timestamp
-   northstar_archive_verification_failures_total

Alert definitions:

ALERT-01: queue depth remains above 90 percent for 3 minutes. Severity:
Critical. First action: inspect validation-worker health and database
write latency.

ALERT-02: API p95 latency exceeds 250 milliseconds for 10 minutes.
Severity: Warning. First action: inspect database query latency and
connection pool usage.

ALERT-03: archive verification fails for any completed monthly export.
Severity: Critical. First action: stop partition deletion and inspect
the export manifest.

ALERT-04: a required monthly partition is missing. Severity: Critical.
First action: create the missing partition through the approved
migration procedure, then verify ingestion.

ALERT-05: a device has not sent an event for 15 minutes. Severity:
Informational. First action: inspect device status and network
connectivity.

11. INCIDENT RUNBOOKS
======================================================================

11.1 Ingestion queue is full

Symptoms: - /v1/events returns HTTP 429. - northstar_queue_depth is
above 90 percent. - ALERT-01 is firing.

Procedure: 1. Confirm that the queue service is reachable. 2. Check
validation-worker process health. 3. Inspect database write latency and
active connections. 4. Check whether a recent deployment introduced
validation delays. 5. Scale validation-worker only after confirming
database capacity. 6. Do not purge queued events as a routine recovery
action. 7. Confirm queue depth is decreasing before resolving the
incident.

11.2 Database connection pool exhausted

Symptoms: - DB-032 errors. - API latency increases. - PostgreSQL may
still accept connections from other clients.

Procedure: 1. Inspect active and idle connections by application name.
2. Check for long-running transactions. 3. Check whether an application
deployment increased pool size. 4. Terminate sessions only under the
database incident procedure. 5. Confirm that the API pool returns to
normal utilization.

The per-instance pool maximum is 40 connections. Increasing it without
checking PostgreSQL max_connections can make the incident worse.

11.3 Missing monthly partition

Symptoms: - Inserts fail near the beginning of a month. - DB-031 appears
in validation-worker logs. - PostgreSQL health checks may still pass.

Procedure: 1. Confirm the missing month from the observed_at value. 2.
Check whether the partition maintenance job ran at 02:20 UTC. 3. Create
the partition using the reviewed migration. 4. Retry only events that
were not committed. 5. Verify successful inserts and queue drainage.

11.4 Archive verification failure

Symptoms: - ALERT-03 is firing. - The export manifest checksum does not
match, or row counts differ.

Procedure: 1. Mark the export as unverified. 2. Prevent detachment or
deletion of the source partition. 3. Compare the source partition row
count with the manifest. 4. Re-run the export to a new object key. 5.
Verify checksums and row counts. 6. Obtain operator approval before
resuming retention cleanup.

======================================================================
12. BACKUP AND DISASTER RECOVERY
======================================================================

PostgreSQL base backups run every day at 01:00 UTC. Write-ahead logs
(WAL) are archived continuously.

The recovery point objective (RPO) is 5 minutes. The recovery time
objective (RTO) is 2 hours for a regional database failure.

A quarterly recovery exercise must restore a backup into an isolated
environment and verify: - database startup, - tenant table counts, -
event partition availability, - API authentication, - representative
event retrieval.

A backup is not considered verified merely because the backup job
reported success. Restoration and integrity checks are required.

Redis is not the source of truth. Cache loss must not cause loss of
accepted telemetry events.

======================================================================
13. CHANGE MANAGEMENT
======================================================================

Database schema changes must follow an expand-and-contract process:

1.  Add backward-compatible schema elements.
2.  Deploy application code that supports both old and new forms.
3.  Backfill data in controlled batches if required.
4.  Verify production behavior.
5.  Remove obsolete schema elements in a later release.

A database migration must include: - migration identifier, - author, -
reason for change, - rollback or recovery plan, - expected lock
behavior, - estimated execution time, - validation query.

Production releases are scheduled for Tuesday or Thursday between 09:00
and 11:00 UTC unless an emergency change is approved.

The release freeze begins on the final business day of each month at
16:00 UTC and ends on the first business day of the next month at 09:00
UTC.

14. GLOSSARY
======================================================================

API: Application Programming Interface; a defined interface through
which software systems communicate.

Backpressure: A mechanism that slows or rejects incoming work when a
downstream component cannot safely process it.

Cursor pagination: A pagination method that uses an opaque position
token rather than a numeric page number.

Idempotency: The property that repeating an operation with the same
identity and content does not create an additional logical result.

RLS: PostgreSQL Row-Level Security, which restricts rows visible or
modifiable under a database policy.

RPO: Recovery Point Objective; the maximum acceptable amount of data
loss measured in time.

RTO: Recovery Time Objective; the target time to restore a service.

WAL: Write-Ahead Log; PostgreSQL’s log of changes used for crash
recovery and replication.

UTC: Coordinated Universal Time.

7. Which PostgreSQL version is used in the standard deployment? 8. What

Multi-hop questions: 9. If an event is observed at 2026-10-31T23:59:00Z,
which monthly partition should contain it? 10. If a client receives HTTP

12. If archive verification fails, may the source partition be dropped?
What must happen first? 13. Which index best supports retrieving the

Cross-section reasoning questions: 17. A deployment increases each API

20. A monthly export has the correct object count but an incorrect

21. A client sends an event with an observed_at timestamp 301 seconds in
